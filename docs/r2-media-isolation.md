# R2 media isolation

DA Chatbot stores customer photos and voice notes in a private Cloudflare R2 bucket. Each client deployment already has its own Render service, Neon database, and `CLIENT_SLUG`. New R2 objects use that same client identity so objects from different clients do not share the same application-level prefix.

## New object layout

For a deployment with:

```env
CLIENT_SLUG=acme-renovation
```

new permanent media is stored as:

```text
clients/acme-renovation/messages/<contact-id>/<timestamp>-<uuid>.<ext>
```

Temporary objects that Meta must fetch use:

```text
clients/acme-renovation/meta-outbound/<contact-id>/<timestamp>-<uuid>.<ext>
```

The client slug and contact path segment are sanitized before they are used in an object key.

## Backward compatibility

This change does **not** rename, copy, or migrate existing R2 objects.

Message rows already persist the complete object key. Reads, byte-range voice streaming, downloads, retries, presigned URLs, and deletes continue to use that stored key exactly as written. Therefore historical keys such as:

```text
messages/123/old-photo.jpg
```

continue to work after client-prefixed uploads are enabled.

If an older/manual deployment does not have `CLIENT_SLUG`, new writes keep the historical unprefixed layout instead of failing. Setup Status exposes that deployment as using `legacy` media isolation mode so it can be corrected deliberately.

## Recommended production isolation

The `clients/<CLIENT_SLUG>/...` prefix provides application-level namespacing. For production clients, use credential-level isolation as well.

Preferred setup per client:

1. Create a dedicated private R2 bucket, for example `da-chatbot-acme-renovation-media`.
2. Create an R2 API token restricted to that bucket with only the object read/write permissions required by the chatbot.
3. Put only that client's R2 credentials and bucket name in that client's Render service.
4. Never reuse one client's R2 token in another client's Render service.
5. Keep public bucket access disabled.

A shared bucket can still use the client-prefixed key layout, but a shared account-wide token can read other prefixes if it is compromised. Per-client bucket-scoped credentials provide the stronger boundary.

## Required environment variables

```env
CLIENT_SLUG=acme-renovation
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET_NAME=da-chatbot-acme-renovation-media
```

`CLIENT_SLUG` is already generated by the normal client provisioning flow. R2 bucket/token creation remains a Cloudflare-side provisioning step unless a future provisioning integration automates it.

## Setup Status behavior

The Media storage check still performs a private upload/delete test. It now also reports the media namespace:

```text
clients/acme-renovation
```

For a correctly isolated deployment, the test object itself must be written under that prefix. If R2 works but the generated key does not match the expected prefix, Setup Status reports a warning.

A legacy deployment without `CLIENT_SLUG` remains operational and the R2 connection check can still be ready, but its metadata/summary shows `legacy` isolation mode rather than pretending client namespacing is enabled.

## Rollout checklist

For an existing client:

1. Confirm the deployment has the correct `CLIENT_SLUG`.
2. Prefer creating a dedicated R2 bucket and bucket-scoped token for that client.
3. Update the client's Render R2 environment variables if moving to dedicated credentials.
4. Deploy the code.
5. Run Setup Status and confirm Media storage reports the expected `clients/<CLIENT_SLUG>` namespace.
6. Send a new image and voice note and confirm both can be viewed/played from Inbox.
7. Confirm historical images and voice notes still open. They should remain on their old stored keys.
8. Confirm an outbound Instagram image can still be delivered through the temporary presigned-object flow.

Do not bulk-rename historical objects merely to match the new prefix. Their stored database keys are already valid and keeping them unchanged is the lowest-risk migration strategy.
